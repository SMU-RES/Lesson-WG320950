# 系统设计说明

## 1. 总体架构

系统采用 Flask 服务端渲染 UI 和适配器分层设计。

1. `src/invoice_app/app.py` 负责上传、结果展示和提交。
2. `src/invoice_app/pipeline.py` 负责串联 QR 检测、QR 裁剪图解码、OCR、LLM、校验和表单生成。
3. `src/invoice_app/adapters/*` 提供本地样例适配器和真实模式适配器。
4. `src/invoice_app/validation.py` 负责字段标准化、一致性判断和唯一键生成。
5. `src/invoice_app/database.py` 负责 SQLite 建表、写入和重复拦截。
6. `src/invoice_app/form_export.py` 负责表单导出。

## 2. 流水线约束

`InvoicePipeline.process()` 先调用检测器生成 `crop_path`，再把 `crop_path` 传给二维码解码器。OCR 接收发票图片。这个输入边界必须保持不变：二维码解码器只能收到裁剪图，不能直接收到整张发票图片。

## 3. 本地样例证据

本次交付使用公开真实电子发票样例作为页面证据。来源是 `guanshuicheng/invoice` 的 `test-invoice/电子发票.png`，MIT License，保存路径为 `evidence/real_samples/real_e_invoice.png`。

原图中二维码可见，证据核验时用临时 zxing-cpp 解码出：

```text
01,10,012001800311,33207675,46.62,20190508,76939056883466677916,E1BD,
```

`evidence/screenshots/01_upload.png` 到 `12_duplicate_popup.png` 是用该样例重新生成的 Web 流程截图。

## 4. 真实模式适配器

设置 `INVOICE_APP_MODE=real` 后，流水线使用以下实现：

1. `YoloQrDetector`：加载 Ultralytics YOLO 权重，默认路径为 `runtime/models/yolo/best.pt`，选择最高置信度二维码框并生成裁剪图和标注图。
2. `OpenCvQrDecoder`：使用 OpenCV 解析 YOLO 生成的 QR 裁剪图，不能接收整张发票图片，也不能替代 YOLO 检测。
3. `PaddleOcrEngine`：启动隔离子进程，使用 PaddleOCR 本地 GPU 识别发票文字。
4. `OpenAICompatibleLlmExtractor`：读取环境中的 `LLM_API_KEY`、可选 `LLM_BASE_URL` 和 `LLM_MODEL`，调用 NVIDIA NIM 的 OpenAI 兼容在线 API；未显式配置时使用 `https://integrate.api.nvidia.com/v1` 和 `meta/llama-3.3-70b-instruct`。

敏感配置放在本地环境变量或不提交的 `.env` 中。新机器运行真实模式前需要安装 `cv2`、`paddleocr`、`paddlepaddle-gpu`、`ultralytics`、CUDA 可用的 PyTorch，并确认 `runtime/models/yolo/best.pt` 存在或设置 `INVOICE_APP_YOLO_WEIGHTS`。`scripts/check_real_mode.py` 可在部署前检查依赖、权重、YOLO/Paddle CUDA 设备配置和密钥；`scripts/train_yolo_qr.py` 提供 YOLO QR 权重训练入口。临时 zxing-cpp 只是证据核验工具，不在运行时链路里。

## 5. 重复报销拦截

表单中的 `unique_key` 由标准化字段生成。SQLite `invoice.unique_key` 带唯一约束。重复提交会触发唯一约束，并返回“重复报销：该发票已存在”。

## 6. 交付脚本

`scripts/package_delivery.py` 支持 `--dry-run` 和 `--zip`，用于检查或生成三段式交付包。顶层结构固定为 `code/`、`演示/`、`报告pdf版本/`：脚本保留默认 YOLO 权重 `code/runtime/models/yolo/best.pt`，把截图放入 `演示/`，把 PDF 报告放入 `报告pdf版本/`，同时排除 `.env`、虚拟环境、缓存、数据库、ZIP、其它模型权重、训练 runs 和运行产物等不应进入交付包的文件。
